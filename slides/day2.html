Continuous batching

The engine rebuilds the batch at every step, not every request

Stepone forward pass
Finished?leave the batch at once
Room?waiting requests join
Next stepa new batch
  • A short answer does not wait for the longest answer in its batch to finish.
  • Two limits decide who joins: the sequence cap (max_num_seqs) and the token budget per step (max_num_batched_tokens).
  • A third limit is not a setting: free cache blocks.

Orca (Yu et al., OSDI 2022) introduced iteration-level scheduling; every current engine does it. Before it, a batch of requests ran until its longest member ended. Sources: Orca paper; vLLM engine arguments page.

Admission

The engine admits a request when its next chunk fits, not its whole answer

  • Admission checks the blocks for the prompt, or the next chunk of it, plus a small reserve.
  • The answer's growth is not reserved: that is why the cache can run out mid-answer.
  • A cap sized from Lab 1.2's arithmetic keeps answers from outgrowing the cache.

This is why the cap matters even with paged memory: the engine is optimistic at admission. The stretch of Lab 2.1 keeps the cap at 48 and limits each step to 512 tokens with 90% utilisation: at 6 users it meets the objective too (96%, no preemptions), because 6 conversations fit. Ask what happens at 20 users: nothing then stops admissions before the cache fills.

Interference

A long prompt processed whole stops every answer in the batch

  • Prefill and decode share each step. A 5,000-token prefill makes one step last over a second.
  • Every running answer waits for that step before its next token: a stall.
  • Averaged over 150 tokens, a one-second stall barely moves TPOT. The visitor sees the whole second.

This is why Musamir's objective has a third clock. DistServe and Sarathi-Serve both describe prefill-decode interference; Sarathi-Serve's answer is the chunked prefill of this session. Sources: arXiv 2401.09670; arXiv 2403.02310.

Chunked prefill

Decode first, then fill the step's token budget with pieces of prompts

Decodesone token per running answer
Budget left?max_num_batched_tokens
Prompt chunkthe next piece that fits

Every step stays short, so no answer stalls. The price: a long prompt needs several steps to its first token.

vLLM's guidance: a smaller budget favours inter-token latency, a larger one favours time to first token and throughput. In vLLM V1 chunked prefill is on by default when the model supports it; Fault 3 switched it off. Source: vLLM optimization page.

Prefix caching

A block is reused only if every token before it is identical

  • Each full block of 16 tokens is hashed together with the hash of the block before it.
  • A new request looks up its blocks in order and stops at the first miss.
  • Reused blocks skip prefill: a shorter time to first token and less work per request.
So: one changing token at the start of a prompt makes every block after it a miss.

vLLM's automatic prefix caching hashes the parent hash, the block's tokens and extra keys such as a cache salt. Ask the room what Musamir's prompt starts with (yesterday's homework): a header with the request number. Source: vLLM design page on prefix caching.

Lab 2.3 · task 4

The shared base text lets one tenant reuse another tenant's blocks

  • Unsalted, 6,000 blocks were reused across tenants in one run.
  • A reused block answers faster, so timing can tell an attacker whether another tenant's prompt starts with a given text.
  • Rawya's rule: no cache block crosses tenants.

The base text is public, so nothing secret leaks here. The rule exists because the tenant parts differ and the next prompt change could put something sensitive early. vLLM's documentation describes this timing attack and the cache_salt defence. Source: vLLM prefix caching design page.

The vendor's offer

A semantic cache returns a stored answer when a question looks similar enough

  • Each question is embedded; the nearest stored question above a threshold returns its stored answer.
  • A hit skips the model entirely: no prefill, no decode.
  • Unlike the prefix cache, a hit can be a wrong answer: the model never sees the new question.

Contrast with Session 3: the prefix cache reuses computed state for identical tokens, and the model still writes every answer. A semantic cache reuses answers. That is a product decision, not an engine setting, and Hanadi owns it.

Lab 2.4 · task 4

Mask before the lookup, refuse to store what carries personal data

  • Phones (05 and 8 digits) and bookings (LW- and 6 digits) are masked before the similarity is computed.
  • An entry whose question carried any is never stored: 42 of 240 refused.
  • A cached answer is served to other visitors; one written for a booking must not be.

Two rules, not one: masking keeps numbers out of the index and logs; refusing keeps answers written for one person away from another. Regexes catch formats, not names; a production system would add a named-entity check. Rawya signs off on this list.

Lab 2.4 · task 5

The decision: no semantic cache on text alone

Decision. No threshold keeps wrong answers under 1 in 1,000 in both languages. Keep the prefix cache, which never returns a wrong answer.

Stretch: keyed on the event, day, venue and ticket as well as the text, the cache hits 9.6% at 0.70 with no wrong answer in the sample.

"No" is a valid engineering answer and the lab checks for it. The stretch shows the condition under which a semantic cache becomes defensible: an extraction step that keys on the slots. That step can itself be wrong, which would need its own evaluation; a good capstone point.
